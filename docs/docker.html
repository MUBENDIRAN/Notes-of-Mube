Docker is a platform used to package and run applications in containers. These notes introduce the container environment, image workflow, common commands, storage, networking, multi-container applications and Swarm.

1. Containers and Docker Engine

What is a container?

A container is a loosely isolated environment that runs within a host machine's kernel and allows application-specific code to run. The notes describe a container environment as having an independent file system and local networks, while running application-specific code.

Docker Engine structure
Docker Engine
Docker serverAPICLI

The Docker server runs the daemon, a background process.

Docker CLI→Docker daemon→Host kernel

The command-line interface sends requests to the Docker daemon through the Docker Engine API. The daemon builds, runs and manages Docker objects such as images, containers, networks and volumes.

Remember: The CLI is the client you type commands into; the daemon is the background service that performs most Docker operations.

2. Containers vs Virtual Machines

The original notes introduce a comparison between containers and virtual machines. At a high level, containers share the host operating-system kernel, while virtual machines run separate guest operating systems on virtualized hardware.

ContainersVirtual machines
Share the host kernel.Run a guest operating system.
Package application code and its dependencies.Include an operating system and application environment.
Typically lighter to start and run.Typically use more resources because each VM includes an OS.

This comparison is a short explanatory summary; the source PDF contains the section heading and comparison illustration, but no detailed written comparison.

3. Docker Images and Docker Hub

Docker image

A Docker image is a read-only template of instructions for creating a Docker container. It defines the container's code, libraries, environment variables, configuration files and other required content. One image can be used to create many containers.

Docker Hub

Docker Hub hosts images in online repositories and allows users to find and obtain images published by other users and organisations.

4. Core Docker commands

Use --help to see command options.

CommandPurpose in the notes
docker search <image_name>Search for an image.
docker create --name=<name> -it <image> bashCreate a container with a name and interactive terminal settings.
docker container lsList running containers. Add -a to include stopped containers.
docker start <container_name>Start a stopped container.
docker attach <container_name>Attach to a running container's input/output stream. The notes list Ctrl + P, then Ctrl + Q to detach.
docker logs <container_name>View container logs.
docker stop <container_name>Stop a container.
docker rm <container_name>Remove a container.
docker run --name=<name> -it <image> bashCreate and start a container.
docker image lsList local images.

The notes explain -it as interactive terminal use. The -i flag keeps standard input open, and -t allocates a pseudo-terminal. docker create creates a container but does not start it; docker run creates and starts it.

Useful additions for day-to-day work

# Show all containers, including stopped ones
docker container ls -a

# Follow a container's logs
docker logs -f <container_name>

# Remove a stopped container
docker rm <container_name>

# Remove a running container forcefully (use carefully)
docker rm -f <container_name>

5. Dockerfiles and directives

A Dockerfile contains instructions used to build an image.

Example directives from the notes

DirectiveMeaningExample
FROMSelects the base image.FROM node:latest
RUNExecutes a command while building the image.RUN npm install -g serve
COPYCopies files and directories into the image filesystem.COPY ./display ./display
WORKDIRSets the working directory for subsequent instructions.WORKDIR /app
CMDDefines the default command to run when a container starts.CMD ["node", "serve.js"]
EXPOSEDocuments the port the application is expected to listen on.EXPOSE 80

CMD formats

The notes show two forms:

# Shell form
CMD serve ./display

# Exec form (preferred in the notes)
CMD ["node", "serve.js"]

Exec form supplies the executable and arguments as a JSON array. Shell form runs through a shell. Exec form is generally preferred for predictable signal handling, especially when the process should run as PID 1.

Important distinction: RUN executes during image build. CMD supplies the default command when a container starts. ENTRYPOINT, not covered in the original notes, is commonly used to define the container's main executable.

Small practical Dockerfile (additional example)

FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
EXPOSE 3000
CMD ["npm", "start"]

This is an illustrative Node.js example, not a Dockerfile copied from the original notes. It assumes the project has a valid lockfile and a start script.

Copying project files

COPY . .

The notes describe this as copying the local project contents into the container's current working directory.

6. Container execution, flags and caching

Run a container in detached mode and publish a port

docker run --name=<name> -d -p 3000:80 <image_name>
  • -d runs the container in detached/background mode.
  • -p 3000:80 maps host port 3000 to container port 80.

Execute a command inside a running container

docker exec -it <container_name> bash

.dockerignore

A .dockerignore file excludes unnecessary files from the build context. The notes list examples such as .git/, node_modules, README.md and package-lock.json.

Layer caching

Docker can reuse cached build layers when the relevant instructions and inputs have not changed. The notes recommend placing dependency installation before copying frequently changing source files.

RUN npm install
COPY . .

This ordering can avoid reinstalling dependencies every time application source files change, provided the dependency inputs remain unchanged. A more reliable Node.js pattern is to copy the package manifest and lockfile first, install dependencies, and then copy the remaining source files.

COPY package*.json ./
RUN npm ci
COPY . .

EXPOSE

EXPOSE 80 documents that the application is intended to listen on port 80 inside the container. It does not publish the port to the host by itself; use -p or another networking configuration to make a port reachable. This is an important distinction: EXPOSE is image metadata/documentation, while -p creates a host-to-container port mapping.

7. Docker storage and mount types

The notes cover three mount types: volumes, bind mounts and tmpfs mounts.

Mount typeHow it worksTypical use from the notes
VolumeDocker-managed persistent storage.Sharing data, logs, database queues and multi-container pipelines.
Bind mountMaps a real host path into a container.Local development loops and exporting artifacts.
tmpfsStores files in memory rather than persistent disk.Short-lived files and sensitive temporary data.

Volume mounts

Volumes are managed by Docker and can be shared across containers. The notes describe them as useful for remote server scenarios and log access.

Bind mounts

Bind mounts connect a host directory to a container directory. They are useful during development, but a process in the container may modify the mounted host files if permissions allow it. Treat this as a security boundary to manage carefully.

tmpfs mounts

tmpfs mounts keep data in memory and the data is removed when the container stops. The notes mention short-lived files, secrets and encryption keys as possible use cases. Ensure the chosen storage and threat model are appropriate before placing sensitive material there.

Mount relationship
Host filesystem— bind mount →Container filesystem
Docker-managed volume— volume mount →Container filesystem
RAM— tmpfs mount →Container memory filesystem

Mount commands

# Create/use a named volume
docker run -it --name=<name> --mount source=myvol,target=/src/shared ubuntu bash

# Remove a volume
docker volume rm <name>

# Bind mount
docker run -it --name=<name> --mount type=bind,source=/users/stuff,target=/src/mountdir <image> bash

# tmpfs mount
docker run -d -it --name=<name> --mount type=tmpfs,destination=/app ubuntu bash

# Inspect a container
docker inspect <container>

8. Docker networking

Docker networks allow containers to communicate with one another and with external networks, depending on the network configuration.

Default network drivers in the notes

NetworkSummary
BridgeThe default bridge network. Containers connected to it receive container IP addresses.
NoneProvides no external container network; the container retains loopback networking.
HostThe container shares the host network namespace and uses host networking.

User-defined private networks

The notes recommend user-defined bridge networks so containers can communicate using container names rather than requiring the user to find each container's IP address. This name-based service discovery is a key advantage over relying on the default bridge network.

# List networks
docker network ls

# Inspect a network
docker network inspect bridge

# Create a network
docker network create PrivateNet

# Run a container attached to that network
docker run -dit --name=<name> --network=PrivateNet busybox

To remove containers in bulk, the notes show:

docker container ls -aq | xargs docker rm -f

9. Docker Compose

Docker Compose is a tool for defining and running applications that consist of multiple containers. In a Compose file, each container configuration is defined as a service, commonly in compose.yaml or docker-compose.yml.

Compose file structure

services:
  players:
    build: ./players

The source notes show a top-level version: '3' field. Modern Docker Compose uses the Compose Specification and does not require a top-level version field; the property is now obsolete/informational. Docker's Compose reference.

Common Compose concepts

  • services: defines the application's services.
  • build: specifies the build context for an image.
  • image: specifies an image to use.
  • depends_on: expresses service startup dependencies.
  • volumes: mounts host paths or named volumes into services.
  • networks: defines networks used by services.

Compose commands

# Create and start services
docker compose up

# Build images before starting services
docker compose up --build

Using bind mounts can make local development faster because source changes can be reflected without rebuilding an image for every edit. Named volumes are more appropriate for persistent application data such as database files.

Practical Compose example (additional example)

services:
  web:
    build: .
    ports:
      - "3000:3000"
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: change-me
      POSTGRES_DB: appdb
    volumes:
      - db_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  db_data:

Additional teaching example. Use a strong secret or environment file rather than committing real credentials. depends_on controls startup order; with service_healthy, Compose waits for the database health check before starting the dependent service.

Multi-container benefit: Compose lets you define related services together, configure their networks and storage, and start the application with one command.

10. Docker Swarm

Docker Swarm is a clustering and orchestration mode in which multiple Docker Engine instances work together as a swarm.

Nodes, managers and workers

  • Node: A machine participating in the swarm.
  • Manager node: Organises the cluster and assigns work to worker nodes.
  • Worker node: Executes assigned tasks and reports status.

Services and replicas

A Swarm service describes the desired state for a workload based on a container image. A service can run multiple replicas across nodes. The notes also mention routing mesh and overlay networking for cluster traffic.

Swarm service flow
Website / Service→Swarm cluster
Engine node 1Engine node 2Engine node 3

Ports listed in the notes

PortProtocolPurpose
2377TCPCluster management communication.
7946TCP and UDPCommunication among nodes.
4789UDPOverlay network traffic.

Swarm commands

# Initialise a swarm
docker swarm init --advertise-addr <ip-address>

# List nodes
docker node ls

# Create a service and publish port 80
docker service create --name=<name> --publish=80:80 <image>

# List tasks for a service
docker service ps <service-name>

# Update the service replica count
docker service update --replicas 6 <service-name>

The notes describe Swarm benefits as load balancing, service discovery and scalability. Swarm mode is built into Docker Engine, but whether it is the right production orchestrator depends on the team's operational needs and platform strategy.

Swarm firewall reminder: Keep cluster ports restricted to trusted nodes. Docker documents TCP 2377 for manager/control-plane communication, TCP/UDP 7946 for node discovery, and UDP 4789 for overlay traffic. Do not expose these ports broadly to the public internet. See the official Swarm tutorial.

11. Docker Hub, cloud registries and references

Container registries store and distribute container images. The notes distinguish Docker Hub from AWS Elastic Container Registry (ECR), noting that ECR is the AWS-managed registry used to store container images in AWS.

Common workflow: build an image, tag it for the target registry, authenticate, and push it to the registry. The original notes mention Docker Hub push and cloud container registries, including AWS ECR.

Example: tag and push to a registry

# Build an image
docker build -t my-app:1.0 .

# Tag it for a registry (example path)
docker tag my-app:1.0 REGISTRY_HOST/PROJECT/my-app:1.0

# Authenticate using the registry's recommended login method
# Then push the tagged image
docker push REGISTRY_HOST/PROJECT/my-app:1.0

Replace the registry path with the actual registry hostname and repository. Authentication commands differ between Docker Hub, Amazon ECR and other registries; use the registry provider's current instructions.
