The notes are a map of pieces that show up in the same products over and over: a URL shortener, a chat app, Instagram, YouTube, Netflix, Uber and Google Drive. Each row below is the definition in the notes, plus the correction where a label is easy to mix up.

Redis is the cache the notes name. It is not the only one. The pattern is “memory in front of the database.” The application still has to decide when a cached value is too old. That shows up again in the cache-aside section.

2. Scaling, protection and feeds

PieceWhat the notes say it doesWhere they use it
CDNServes content from a server near the user, which cuts latency.Instagram, YouTube, Google Drive, Netflix.
ShardingSplits a large database into smaller parts so it can grow. Part 5 is the row split versus the column split.URL shortener, chat, Instagram.
ReplicationKeeps copies on more than one server, for availability and for surviving a failed machine.Almost every production system in the notes.
Rate limitingCaps how many requests a client can make, so one caller cannot abuse the API.Login, public APIs, chat.
Unique IDsGives every record an identifier that does not collide. The notes' examples are Base62 and a distributed ID generator.URL shortener, chat, YouTube, Google Drive.
Feed generationBuilds the list of posts a person sees. The two strategies are fan-out on write and fan-out on read.Instagram, Facebook, LinkedIn.

A replica can be updated with the write, or after it. Waiting for the copy makes the write slower and can stall when the network between the copies breaks. Updating the copy afterwards keeps the write fast, and a reader can briefly see the older value. That is the same trade the CAP section names.

Base62 writes an ID. It does not invent one. The notes list “Base62” next to “distributed ID generators,” as if both create uniqueness. Base62 is an alphabet of 62 symbols, digits plus upper and lower case, used so a big number fits in a short URL. The uniqueness comes from the generator: a counter, a UUID, or a distributed scheme such as Snowflake that packs time, a worker number and a sequence into one value. Encoding that value as Base62 does not add new uniqueness. Two generators that emit the same number still collide after encoding.

Fan-out on write and fan-out on read

When the feed is builtWhat gets slower
Fan-out on write (push)The moment the post is created, a copy is delivered to each follower's inbox.The write. A celebrity with millions of followers turns one post into millions of inbox rows. The read is a lookup.
Fan-out on read (pull)The post is stored once. The feed is assembled when someone opens it.The read. The write stays cheap.

The notes stop at those two. A production feed often mixes them: push for ordinary accounts, pull for accounts whose follower list would make the write too heavy. That mix is not a third row in the PDF.

3. Discovery, media and file sync

PieceWhat the notes say it doesWhere they use it

The search index the notes are pointing at is an inverted index: words point at the documents that contain them, so the query does not walk every row. Transcoding is what produces the ladder of files. Adaptive bitrate is the player choosing a rung of that ladder from the current bandwidth and buffer, rather than the server guessing once. If two edits conflict, the simple rule is last write wins, and one edit disappears. A merge keeps both. The notes name the problem and not the rule.

4. Location, chat and pipelines

Analytics pipelineCollects activity so the product can measure it and feed the recommender.YouTube, Netflix.
A retry without a limit makes the outage worse. The notes say to retry after a delay. That is safe only when repeating the operation does not create a second charge, a second email, or a second row. Wait longer after each failure, stop after a fixed number of tries, and put the message on the dead letter queue. The queue is the notes' place for work that has already failed repeatedly. Retrying immediately, with no cap, turns one slow dependency into a pile of identical requests.

Presence is usually a heartbeat. The client refreshes a short-lived “online” flag. When the refresh stops, the flag expires and the user looks offline. That mechanism is not drawn in the notes.

5. Horizontal and vertical sharding

Sharding, in the notes, means splitting one large database into smaller databases so the data is spread across servers. The aim is more data, faster queries, and no single database carrying the whole load.

What is splitWhat stays the sameWhy the notes do it
HorizontalRows. Different servers hold different records.The columns. Each shard has the same shape of table.The data no longer fits on one machine. Their example is Instagram.
VerticalColumns. Different tables, or different databases, hold different fields of the same logical record.The row identity. Profile details are their example: the wide set of fields is pulled apart.A narrower table, so a query does not drag columns it does not need. They call this an optimization.
Vertical sharding is not a bigger machine. The notes' vertical split is columns. Vertical scaling is a different phrase: a larger CPU, more RAM, a bigger disk, still one machine. Horizontal scaling is more machines. Horizontal sharding is one way to scale horizontally. Buying a larger server does not, by itself, split a table.

The notes say “same column, different rows.” Read that as the same columns. A shard that dropped a column would no longer be a horizontal split of that table.

6. Cache-aside and denormalization

Cache-aside is the notes' read path. The application, not the database, talks to the cache.

Cache-aside, the path in the notes
Ask Redis→Hit: return it
Miss→Read SQL→Write Redis→Return
A value with no expiry is a stale answer that looks fast. The notes' path fills Redis on a miss and then trusts it. After an update, that copy is wrong until something removes it or it expires. Set a time to live, or delete the key when the row changes. On a popular miss, many requests can all run the SQL at once. A short lock, or a single request that fills the cache while the others wait, is the usual guard. Neither guard is in the PDF.

Denormalization is the notes' choice to store a copy of data so a read does not join. Reads and analytics get simpler. The cost, which the notes do not spell out, is on the write: every copy has to change, or the copies disagree. Normalization, and why the join existed in the first place, is in the SQL notes.

7. CAP

The three letters in the notes are consistency, availability and partition tolerance. Their slogan is that a distributed system can guarantee only two of the three.

LetterDefinition in the notes
ConsistencyEvery node shows the same data. A write of x = 10 is what every node returns immediately afterwards.
AvailabilityThe system answers. The notes say the user still gets a response when some nodes have failed.
Partition toleranceThe system keeps operating when the network between servers fails.
LabelWhat is keptWhat is given upExample in the notes
CPConsistency and partition tolerance.Availability. During a network split, some requests are rejected rather than answered with a stale or divergent value.ZooKeeper.
APAvailability and partition tolerance.Consistency. A reader can see an older value. The notes call this “eventually consistency.” The adjective is eventually consistent.DynamoDB, in the mode that serves eventually consistent reads.
CAConsistency and availability.Partition tolerance. The notes say this is only possible when a partition is not considered, and that it is mostly theoretical for a distributed system.A traditional single-node SQL database.
During a partition, the choice is consistency or availability. The “two out of three” line is the slogan in the notes. A system that runs on more than one machine will have network failures, so partition tolerance is not a feature you opt out of. When the network splits, a CP system refuses some requests so it does not serve two different values. An AP system answers anyway, and the copies catch up later. CA describes a system that assumes the network never splits. A single database server matches the notes' example because there is no network between replicas. If that one server is down, nobody gets an answer, so it has not escaped failure. It has escaped the distributed choice.

CAP consistency means a read returns the most recent write, or an error. It does not mean “the nodes agree about an old value.” Availability, in the theorem, means a node that has not crashed still responds, including while it cannot reach the others. A node that has crashed is not required to answer.

8. Round robin, thrashing, triggers and interfaces

The last part leaves system design for four ideas the notes want next to it. Scheduling and paging are developed in the operating system notes. The Python side of an interface is in the Python notes.

Round robin

Each process gets a fixed slice of CPU, the time quantum. If it is still running when the slice ends, the scheduler stops it, puts it at the back of the ready queue, and runs the next process. The notes' quantum is 2 ms, with three bursts: P1 is 5 ms, P2 is 3 ms, P3 is 4 ms. Assuming they are all ready at the start, in that order, the slices are:

Those three bursts, quantum 2 ms
P1 · 2→P2 · 2→P3 · 2→P1 · 2→P2 · 1→P3 · 2→P1 · 1

P2 finishes at 9 ms, P3 at 11 ms, P1 at 12 ms. The diagram is the schedule those numbers produce. The PDF gives the numbers and not the timeline.

What the notes list as an advantageWhat they list as a cost
Fair. No starvation. A short quantum keeps response time low, because a new process does not wait behind a long one.A quantum that is too small spends the CPU on context switches. A quantum that is too large stops preempting, and the schedule behaves like first come, first served.

Thrashing

Thrashing is the notes' name for the state where the CPU spends more time moving pages between RAM and disk than running the processes. Their picture is a machine with 4 GB of RAM and an application that wants 8 GB, so the operating system keeps swapping pages in and out. The symptoms they give are a very slow system, high disk use, and low CPU use.

The machine has not run out of RAM entirely. The notes' bullet says “no physical memory.” There is memory. The working set does not fit in it, so a page is evicted and then needed again immediately. The CPU waits on the disk, which is why utilization looks low while the system feels stuck. A page fault itself is not thrashing. Thrashing is that fault happening so often that useful work stops. The operating system notes separate a fault from “RAM is full.”

Triggers

A trigger is a database object that runs when a row is inserted, updated or deleted. The notes list those three events. The trigger runs as part of the statement that woke it. If the trigger fails, the original write can be rolled back with it. That hidden work is why a trigger is easy to forget while debugging a simple insert. The language around tables and events is in the SQL notes.
