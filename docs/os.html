An operating system shares the CPU, memory and other hardware among programs, and it keeps those programs from corrupting one another. These notes cover processes and threads, memory, the schedulers that choose who runs next, and the tools that keep shared data and shared resources from colliding.

1. Processes, threads and system calls

What the notes say
ProcessAn independent execution with its own memory. A process has its own address space.
ThreadA lightweight execution inside a process. Threads of one process share that process's memory. Each thread still has its own stack and registers, so they can run different functions at the same time.

Process states

The notes list five states in a line: New, Ready, Running, Waiting, Terminated. Those are the states. A process does not have to walk that line only from left to right.

How a process moves
New→Ready→Running→Terminated
Running→Waiting→Ready

Running also returns to Ready when the scheduler takes the CPU away. Waiting is often called blocked.

  • New: the process is being created.
  • Ready: it can run, and it is waiting for the CPU.
  • Running: it is on the CPU.
  • Waiting: it cannot run until an event arrives, such as disk or keyboard input.
  • Terminated: it has finished, or it was killed.

Context switching

The notes describe a context switch as the CPU moving from one process to another. The kernel saves the registers and program counter of the process that was running, and restores the next one. That cost is the price of multitasking: more than one program makes progress on one CPU. A switch between two threads of the same process is usually cheaper, because they already share an address space. A switch between processes also has to switch the memory map.

System calls

A system call is the interface a user program uses to ask the kernel to do something the program is not allowed to do itself. The notes give fork() and exec(), which are Unix calls. Opening a file or creating a process goes through this boundary. The program crosses from user mode into kernel mode and back.

pid = fork()
# In the parent, pid is the new child's process id.
# In the child, pid is 0.
# fork() failed if pid is -1.

exec()
# Replaces the program running in this process.
# The process id stays the same.

fork() duplicates the calling process, which is the notes' definition. The two processes then diverge because the call returns a different value in each. exec() does not create a process. It loads a new program over the one that called it. A shell starts a command by forking, then the child calls exec().

The return values are the usual Unix behaviour of fork(). The original notes name the call and say that it duplicates the caller. Windows does not use fork(). Its process and thread model is linked in the references.

2. Memory management

Paging

Paging divides memory into fixed-size blocks. A process is split into pages. Physical memory is split into frames of the same size. The notes' example is a 12 KB program and a 4 KB page, which is exactly 3 pages.

That example wastes nothing because 12 divides by 4. The notes say paging avoids wasting memory. It avoids external fragmentation: free frames can be used even when they are not neighbours. A program that is not an exact multiple of the page size still leaves unused bytes in its last page. That leftover is internal fragmentation. A 13 KB program with 4 KB pages needs 4 pages.

Segmentation

Segmentation divides memory by meaning rather than by a fixed size: code, data and stack are typical segments. The notes connect this with modular programming, because a module can sit in its own segment. Segments have different lengths, so loading and unloading them can leave holes that are too small for the next segment. That external fragmentation is the problem paging was built to avoid.

Virtual memory

Virtual memory lets a process use addresses that are not all in RAM at once. Pages that are not resident sit on disk, in swap or a page file. The notes describe this as using disk as memory.

A page fault is not only a full-RAM event. The notes say a page fault occurs when the data is not in RAM, and then “when RAM is full.” A fault happens whenever the CPU touches a virtual page that is not resident. The page may never have been loaded, or it may have been written out earlier. If RAM has a free frame, the kernel loads the page into it. If RAM is full, the kernel first chooses another page to evict, which may write that page to disk.
A page fault
CPU uses a virtual address→Page not in RAM→Load the page→Resume the process

3. CPU scheduling

The scheduler decides which ready process runs next. The notes ask for the trade-off between throughput, how much work finishes, and waiting time, how long a process sits in the ready queue. A policy that finishes short jobs quickly can leave a long job waiting. A policy that shares the CPU evenly spends time on context switches.

AlgorithmWho runs nextTrade-off in the notes
FCFSFirst come, first served. Processes run in arrival order, and each runs until it blocks or finishes.The notes call it simple, but slow for long jobs. The delay actually hits the short jobs stuck behind a long one. That convoy effect raises their waiting time. The long job itself is not slowed once it has the CPU.
SJFShortest job first. The ready process with the smallest CPU burst runs next.The notes call it fast, and say long jobs can starve. Average waiting time is low when the burst times are known. A long job waits as long as shorter jobs keep arriving. The OS usually has to estimate the next burst. It cannot see the future.
Round RobinEach process gets the same time slice, then goes to the back of the ready queue.Fair, and a good fit for time-sharing, which is the notes' judgement. A very large slice behaves like FCFS. A very small slice spends most of the time switching.
PriorityThe highest-priority ready process runs first.The notes call it efficient, and say a low-priority task can starve. It is the right rule when some work must go first. Starvation is the cost. Aging raises the priority of a process that has waited, so a low-priority job eventually runs. Aging is not named in the original notes.
Multilevel queueProcesses are grouped by type, such as system, user and batch. Each queue can have its own rule.The notes say this is used in complex systems for better control. A system queue can be scheduled ahead of a batch queue. A multilevel feedback queue, a related design, can also move a process from one queue to another. The notes describe fixed groups, not that movement.

4. Race conditions and the critical section

A race condition is what the notes describe: several threads use the same shared data, and the result depends on the order of their steps. The bugs are real and hard to repeat, because a different interleaving produces a different answer. Concurrent reads of data that nobody is changing are not a race. The trouble starts when at least one of the accesses writes.

The critical section is the part of the code that touches that shared data. The notes' rule is that only one process runs inside it at a time. Everyone else waits until that process leaves. That mutual exclusion is what keeps the race from happening in that region.

5. Semaphores, mutexes and deadlock

Semaphores

A semaphore is a counter that controls entry to a shared resource. The notes use wait() and signal(). wait() decreases the counter and is how a process enters. signal() increases it and is how a process leaves. If the counter is zero, wait() blocks instead of letting another process in.

wait(S):
    if S is 0, block
    S = S - 1

signal(S):
    S = S + 1
    wake one process that is waiting on S

A binary semaphore starts at 1, so one process can be inside. A counting semaphore starts at N and lets up to N processes in. The notes say the semaphore “prevents multiple processes from entering once.” That sentence is the binary case: they must not enter at the same time. The counter is what makes the more general form.

Mutex

A mutex is a lock. The notes define mutual exclusion as one holder at a time, which stops concurrent writers from corrupting the shared data. The thread that locks a mutex is the thread that should unlock it. A binary semaphore can be used for the same exclusion, but it does not record an owner.

Deadlock

Deadlock is the notes' picture of two or more processes waiting for each other forever. All four of these conditions are present when it happens. The notes' prevention rule is to break at least one of them.

ConditionMeaning in the notes
Mutual exclusionOnly one process uses the resource at a time. The notes write “mutual exclusions.”
Hold and waitA process holds one resource and waits for another.
No preemptionThe OS cannot forcibly take the held resource away.
Circular waitA waits for B, and B waits for A. Longer cycles count too.

A printer and a disk are enough to show the cycle. Process A holds the printer and waits for the disk. Process B holds the disk and waits for the printer. Neither can continue. Giving every process a fixed order, such as “always take the disk before the printer,” breaks circular wait. That ordering is the prevention method the notes name.

Banker's algorithm is avoidance, not prevention. The notes place it next to resource ordering, under prevention. Ordering removes a deadlock condition. The banker's algorithm leaves the conditions in place and refuses a request that would leave the system unsafe. An unsafe state means deadlock might occur, not that it already has.

Before the grant, each process has declared the most it will ever need. The state is safe when there is an order in which every process can receive its remaining need, finish, and return what it holds. The OS allows the request only when that order would still exist afterwards. If no such order exists, the request waits.
