Git & GitHub Actions

Git is a distributed version control system used to record project history and collaborate. These notes cover the local Git workflow, the commands used to inspect and share that history, and GitHub Actions as the CI/CD layer that runs automated work when repository events happen.

1. Git architecture

The notes introduce Git as Global Information Tracker, a system built to handle everything from small projects to very large ones with speed. In the Git manual, “global information tracker” is a playful expansion used when Git is working well. The name itself is the short command Linus Torvalds chose; it is not a formal acronym.

A change moves through three local areas before it reaches a remote host. The notes draw that path as files in a working directory, a staging area, and then commit history in the local repository.

From working files to a remote
Files
(html, css, js)→Working directory→Staging area
index / cache
git add
Local repository
commit history · HEAD
git commit→Remote host
GitHubGitLabBitbucketAWS CodeCommit
  • Working directory: the project files you edit.
  • Staging area: the snapshot you prepare with git add. The notes also call this the index or cache. Those are names for the same area.
  • Local repository: the commit history. HEAD points at the current commit on the current branch.
  • Remote: a hosted copy. The notes list GitHub, Bitbucket, AWS CodeCommit and GitLab.
Remember: git commit records what is staged. Edits that are still only in the working directory are not part of that commit.

2. Essential commands

Set an identity before the first commit. Git stores the name and email on each commit so history shows who made the change. --global writes those settings for the current user, not for one repository only.

CommandPurpose in the notes
git config --global user.name "name"Sets the name recorded on commits.
git config --global user.email "mail.com"Sets the email recorded on commits.
git config -lLists configuration, including name, email and aliases.
git initTurns the current directory into a Git repository.
git statusShows the state of the working directory and the staging area.
git add <files>Stages the named files.
git rm --cached <files>Removes files from the index and leaves the copies in the working directory.
git add -A or git add .Stages new, modified and deleted files.
git commit -m "content"Records the staged snapshot in local history with that message.
git logShows commit history: author, time and the unique commit hash.

git rm --cached is the command to use when a file should stop being tracked but should stay on disk. If the file was already committed, the next commit records the deletion from the repository. Add the path to .gitignore if Git should keep ignoring it.

The notes list git add -A and git add . together. In current Git, both stage new files, modifications and deletions. git add -A covers the whole repository. git add . covers the current directory and everything under it.

A short local loop

git init
git status
git add .
git commit -m "Start the notes"
git log

Useful additions for day-to-day work

# Compact status
git status -sb

# Recent history as one line per commit
git log --oneline --graph --decorate -n 15

These two commands are reading aids. They are not in the original notes.

3. History, restore and amend

CommandPurpose in the notes
git show <hash>Shows one commit, including its diff.
git diffShows changes in working files compared with the staging area or the last commit.
git restoreRestores working-tree files, or discards the latest uncommitted changes.
git commit --amend -m "message"Replaces the latest commit message, or updates that commit with newly staged changes.

git diff with no extra flags compares the working directory with the staging area. To see what is already staged against the last commit, use git diff --staged. The notes describe both comparisons under the one command.

# Discard unstaged edits in one file
git restore <file>

# Unstage a file and keep the working copy
git restore --staged <file>

# Replace the message on the latest commit
git commit --amend -m "Clearer message"
Amend with care: --amend rewrites the latest commit and gives it a new hash. Use it while that commit is still only on your machine. If you already pushed it, rewriting it changes history that other people may have fetched.

git restore <file> throws away uncommitted edits in that file. It does not change commits that are already in history.

4. Remotes and push

A remote is the hosted repository your local history is connected to. The notes use the conventional remote name origin.

CommandPurpose in the notes
git remote add origin <URL>Connects this local repository to a remote URL.
git branchLists local branch names, such as master or main.
git branch -M mainRenames the current branch to main.
git pushSends committed local changes to the remote.
git branch -rLists remote-tracking branches.
git branch -aLists local and remote-tracking branches.

-M is a forced rename of the current branch. The notes use it so the local branch matches the main name expected by many remote hosts. The first push of a new branch also needs an upstream. A common form is:

git push -u origin main

The original notes show git push on its own. The -u form is an additional setup step so later git push and git pull know which remote branch to use.

5. Branches, merge and rebase

A branch is a movable name for a line of commits. The notes use a feature branch, then bring that work back with merge or rebase.

CommandPurpose in the notes
git branch <name>Creates a branch. It does not switch to it.
git checkout <feature-a>Switches the working branch to feature-a.
git checkout -Switches back to the previous branch.
git branch -d <name>Deletes that local branch.
git merge <branchname>Merges the named branch into the branch you are on.
git pull -r origin masterFetches remote updates and rebases the local branch on top of them.
git rebase --continueContinues a rebase after conflicts are resolved.
git branch feature-a
git checkout feature-a
# edit, add, commit
git checkout main
git merge feature-a
git branch -d feature-a

git pull -r is git pull --rebase. The notes use origin master. If the remote branch is main, the matching command is git pull -r origin main. Rebase takes your local commits and replays them after the commits just fetched from the remote.

If a rebase stops on a conflict, fix the files, stage the resolutions with git add, then run git rebase --continue. git rebase --abort returns the branch to the state it had before that rebase started.

Merge and rebase do different jobs: merge joins two lines of history and can add a merge commit. Rebase rewrites your local commits so they sit on top of the updated remote branch. Rebase local commits that have not been shared, or agree with the team before rewriting commits that others already have.

Current Git also has git switch <branch> and git switch -c <name> for changing and creating branches. The notes use git checkout, which still performs those branch switches. git branch -d refuses to delete a branch that is not fully merged. git branch -D deletes it anyway.

6. GitHub Actions

GitHub Actions is the CI/CD platform in the notes: continuous integration and continuous deployment. It automates build, test and deployment pipelines inside a GitHub repository.

  • Workflow triggers: a workflow can build and test every pull request, or deploy pull requests after they are merged.
  • Beyond a deploy pipeline: workflows can also run on other repository events, such as a new issue or a release tag.
  • Workflow: a configurable automated process that runs one or more jobs.
  • YAML file: the workflow definition, checked into the repository. GitHub runs it when an event happens, when someone starts it manually, or on a schedule.
  • What a workflow can do: build, test, package, release and deploy a project on GitHub.

GitHub reads workflow files from .github/workflows/. A push to the default branch, a pull request, workflow_dispatch for a manual run, and schedule with a cron expression are the trigger styles the notes describe.

What runs a workflow
Event, manual run, or schedule→Workflow YAML→One or more jobs→Runner

7. Runners, variables and artifacts

Runners

A runner is the machine that executes a workflow when its trigger and job dependencies are met. GitHub-hosted runners are fresh virtual machines. The notes list separate runner images for Linux, Windows, macOS and more. A job selects one with runs-on, for example ubuntu-latest.

If those hosted images are not enough, the notes say to add a self-hosted runner. That is a machine you register with the repository or organisation. The workflow then uses that runner instead of a GitHub-hosted image.

Why the notes use self-hosted runners

ReasonWhat the notes are solving
Software dependencyBuild or test tools that are not on the hosted runner images.
VM size and configurationLarger or specialised hardware for heavy jobs.
Secure access and networkingA private network, internal services, or a security policy the hosted runners cannot meet.
Self-hosted caution: a self-hosted runner can reach whatever that machine can reach. Do not let untrusted pull-request code run on a runner that holds private network access or long-lived credentials. GitHub documents this boundary in its self-hosted runner guidance.

Environment variables

The notes set custom variables with an env map and read them where a step needs them. A workflow can also read the default environment variables GitHub sets on every runner, and it can read workflow or runner details through GitHub contexts such as github, runner, env and secrets.

env:
  APP_ENV: staging

jobs:
  show:
    runs-on: ubuntu-latest
    steps:
      - run: echo "APP_ENV is ${APP_ENV}"
      - run: echo "Repo ${GITHUB_REPOSITORY} at ${GITHUB_SHA} on ${RUNNER_OS}"

APP_ENV is a custom variable from the notes' env: pattern. GITHUB_REPOSITORY, GITHUB_SHA and RUNNER_OS are default environment variables. The full list is in GitHub's variables reference. Do not print secret values into logs.

Artifacts

Artifacts share files between jobs and keep those files after the workflow finishes. A later job downloads what an earlier job uploaded. The stored files remain available on the workflow run for the retention period configured on the repository.

- uses: actions/upload-artifact@v4
  with:
    name: build-output
    path: dist/

- uses: actions/download-artifact@v4
  with:
    name: build-output
    path: dist/

Upload and download are the mechanism behind the notes' “share data between jobs, and store data once the workflow has completed.” Keep secrets and credentials out of artifacts.

8. Starter workflow

This workflow is an additional teaching example. It is not copied from the original notes. It builds the ideas from the GitHub Actions page into one file: a trigger, one job, a hosted runner, a checkout of the commit, and a test command.

name: CI

on:
  pull_request:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run tests
        run: echo "Replace this with the project's test command"

Save it as .github/workflows/ci.yml. A pull request, or a push to main, starts the test job on a fresh Ubuntu runner. Replace the echo step with the real test command for the project.
